# 出片片段生成的可见性、取消与观看设计

日期：2026-11-21　分支：langchain　状态：待设计审查（同日修订两次：任务列表扩成全局的个人任务队列，见 §8.5；每条任务定位到小说 › 章节 › 片段与镜号，见 §8.6）

相关设计：`docs/specs/2026-11-11-film-node-graph-design.md`（节点图与片段卡）、`docs/specs/2026-11-12-minimax-provider-design.md`（厂商接入）、`docs/specs/2026-11-12-frontend-routing-design.md`（路由与一次性 state）、`docs/specs/2026-11-13-backend-i18n-design.md`（消息登记）。

实施计划：`docs/plans/2026-11-21-film-task-visibility.md`。

## 1. 背景

2026-11-21 用户实测出了一段（E01-C01，约 4–5 分钟成功，花费 ¥7.5），过程里碰到四个问题：

1. **看不出进度和预计时长**。片段卡上只有「生成中 · 已等 m:ss」，不知道正常要等多久，等了 4 分钟分不清是慢还是坏了。
2. **任何任务列表里都没有出片任务**。任务铃铛和动态面板只列转换任务；离开画布后，出片在不在跑、跑完没有，完全看不到。
3. **没有取消按钮**。点错了、等烦了都只能干等。
4. **出完的视频找不到明显的地方看**。结果只在卡片上悬停时静音循环，或者在侧栏尝试表里点一个小字链接。

## 2. 目标与非目标

目标（用户已确认方向）：

1. 任务铃铛点开的面板是**全局的个人任务队列**：任何页面都能打开，铃铛上是进行中的数量；覆盖本人的所有异步任务（转换、出片片段、成片合成）；分「进行中」「已结束」两个区；每条定位到小说 › 章节 › 片段与镜号，点击跳到对应位置；只有本人看得到（§8.5、§8.6）。
2. 生成中的片段卡写明「已等 m 分 s 秒 · 通常 x–y 分钟」。
3. 可以取消：厂商支持就真取消；不支持就「不等了」，并在确认框里明说服务商可能仍会生成并扣费。取消之后厂商那边后来完成的结果怎么处理，要有明确规则（§5.4）。
4. 出完的片段卡上有明显的播放按钮，点开是带声音与控制条的播放窗口；完成时发通知，点通知直接打开播放。
5. 中英双语。

**硬性规则：普通用户界面的新增内容绝不出现厂商名或模型名**（MiniMax、Seedance、ARK、方舟、海螺……以及 `provider` / `model` 的值）。等待时长只说「通常 x–y 分钟」。

非目标（本次不做）：

- 真实进度百分比（两家厂商的查询接口都不给进度）。
- 批量「全部取消」。
- 取消转换任务、取消合成（后端都没有中止机制，见 §8.5 的表）。
- 管理后台的任务页纳入出片任务。
- 左侧栏、书架上的「在跑」标记纳入出片任务（它们仍只反映转换任务）。
- 清理现有界面里已经暴露的厂商名（见 §10.1，另开一件事）。
- 把转换任务也并进同一个聚合接口（理由见 §8.5）。

## 3. 各厂商的取消能力（结论与依据）

查的是两家的官方接口文档（2026-11-21 读取）。

### 3.1 MiniMax

接口：`DELETE /v2/video_generation/{task_id}`（文档：`https://platform.minimax.cn/docs/api-reference/video-generation-v2-delete`）。行为随任务状态不同：

| 任务状态 | DELETE 的效果 |
|---|---|
| `queued`（排队中） | **取消**，响应 `action: "cancelled"`；文档写明「尚未开始处理，无扣费」 |
| `running`（生成中） | 不可操作，报错 |
| `cancelled` | 不可操作，报错 |
| `succeeded` / `failed` | **删除任务记录**，响应 `action: "deleted"` |

响应体：`{ task_id, action, status }`。

### 3.2 火山方舟 Seedance

接口：`DELETE /api/v3/contents/generations/tasks/{id}`（文档：`https://docs.volcengine.com/docs/82379/1521720`）。

| 任务状态 | DELETE 的效果 |
|---|---|
| `queued` | **取消排队**，任务状态变为 `cancelled` |
| `running` | 不支持 |
| `succeeded` / `failed` / `cancelled` / `expired` | **删除任务记录**，之后查不到 |

成功响应是空对象 `{}`。

### 3.3 结论

- 两家都**只能取消还在厂商那边排队的任务**，一旦开始生成就停不下来，也照常计费。
- 两家的 DELETE 对已结束的任务都是**删除记录**——如果不看状态直接发 DELETE，碰上刚好跑完的任务会把结果的记录删掉，钱花了还拿不到视频。所以实现必须**先查状态，只有 `queued` 才发 DELETE**；查询与删除之间任务若刚好开始生成，DELETE 会被拒绝（报错），按「没取消成」处理，不会误删。
- 因此产品上有两种取消：
  - **真取消**：我们这边还没提交，或已提交但厂商确认取消。不花钱。
  - **不等了**：厂商已经在生成。我们立刻放开这一段，厂商那边继续跑、可能照常计费；结果回来后的处理见 §5.4。
- 实测中多数时候任务提交后很快进入生成，所以用户点到的大多会是「不等了」。确认框的文案按这个现实写（§7.3）。

### 3.4 厂商接口的实现约定

`backend/render/providers/base.py` 的协议新增：

- `typical_sec: tuple`——一段通常要等多久（秒，下限、上限）。只给界面显示，不参与任何判定。
- `cancel(task_id) -> bool`——`True` 表示厂商确认已取消且不计费；取消不了返回 `False`。

公共函数 `try_cancel(provider, task_id) -> bool` 包住它：厂商没有 `cancel`、调用抛任何异常，都返回 `False`，绝不外抛，日志脱敏。调用方因此只有两个分支。

| 厂商 | `cancel` 的实现 | `typical_sec` | 依据 |
|---|---|---|---|
| MiniMax | GET 查询，`status == "queued"` 才 DELETE，返回 `action == "cancelled"` | (180, 420) | 2026-11-21 实测一段 4–5 分钟，取 3–7 分钟 |
| Seedance | GET 查询，`queued` 才 DELETE，再 GET 确认状态为 `cancelled` | (120, 480) | **没有实测**，保守值，待实测后校正 |
| 假厂商（测试） | 可配置成败 | (60, 180) | — |
| 没给的厂商 | — | (60, 600) | 缺省 |

Seedance 的 DELETE 成功响应是空对象，分不清「取消了」还是「删除了」，所以多查一次确认。

## 4. 数据结构

一个版本一份 `session.json`（`backend/render/session.py`）。**不新增段状态**——段仍是 `planned / queued / running / downloading / done / failed / stale`；取消后段回到它「不在跑时该在的状态」（没有采用过 → `planned`；有采用 → `done`，提示词改过则 `stale`）。这样现有的状态标签、计数、筛选都不用动。

新增的只有：

**尝试（`attempts[]`）的两种状态**

| 状态 | 含义 |
|---|---|
| `cancelled` | 厂商确认取消，不计费。带 `cancelled_at` |
| `abandoned` | 用户不等了，厂商可能还在跑。带 `cancelled_at` 与 `billing` 快照 |

`billing = { provider, model, resolution, duration, estimate_cny }` 是取消那一刻的会话设置。之后用户可能改厂商或档位，这次尝试的查询、下载、记费都按快照来。

`abandoned` 有了结果后变为终态，并带 `settled_at`：

- 成功 → `succeeded`，外加 `late: true`（「取消后才出的结果」），文件照常落盘；
- 厂商失败 → `failed`；厂商那边显示已取消 → `cancelled`；
- 一直查不到（§5.4）→ `failed`，错误为 `film.cancel.lost`。

**段 / 自由节点的两个字段**

- `ended_at`：这一条最近一次结束的时间；
- `ended_as`：`done` / `failed` / `cancelled`。

任务列表的「最近结束」靠它们；出片线程里每一处让段进入终态的地方都写。

**会话视图**

`view()["options"]` 增加 `typical_sec: [下限, 上限]`（当前厂商的），片段卡用它显示「通常 x–y 分钟」。

## 5. 取消

### 5.1 三种结局

接口响应带 `cancel_outcome`：

| 结局 | 条件 | 会话里发生什么 | 钱 |
|---|---|---|---|
| `dequeued` | 段是 `queued`，还没提交给厂商 | 段回到不在跑的状态，不留尝试 | 不花 |
| `cancelled` | 已提交，厂商确认取消 | 最后一次尝试记 `cancelled`，段放开 | 不花 |
| `abandoned` | 已提交，厂商取消不了（或取消出错） | 最后一次尝试记 `abandoned` 加 `billing`，段放开，出片线程后台继续盯 | 可能照常计费 |

「放开」的意思是这一段立即回到可操作的状态：可以改提示词、重出、合成（用原来采用的那次）。

### 5.2 不能取消的情形（409）

| 情形 | 消息代码 | 文案 |
|---|---|---|
| 正在提交（请求在路上，还没拿到任务号） | `film.cancel.submitting` | 正在提交，几秒后再取消 |
| 已生成完、正在取回（`downloading`） | `film.cancel.finished` | 这一段已经生成完成，正在取回，不用取消了 |
| 不在排队或生成中 | `film.cancel.not_running` | 这一段不在排队或生成中 |
| 两步之间状态变了（§5.3） | `film.cancel.changed` | 状态刚刚变了，请再试一次 |

「正在提交」的窗口只有一次厂商请求那么长。这时既不能本地取消（请求已发出），也拿不到任务号去取消，所以让用户几秒后再点，而不是做一个「等提交回来再取消」的排队机制。

### 5.3 两步取消与并发

厂商调用不能放在会话锁里（一次请求可能几秒）。所以接口分两步：

1. `cancel_target(root, item)`：锁内看一眼，得到「任务号或 None」和厂商名，不改会话；
2. 锁外 `try_cancel(provider, task_id)`（有任务号才调）；
3. `cancel(root, item, task_id, confirmed)`：锁内再判一次，和第 1 步看到的任务号对不上就抛 `film.cancel.changed`；对得上就落账。

出片线程同时在跑也没关系：它对一个段的每次改动都在锁里，并且只处理状态仍在跑的段；取消落账后段已不在跑，线程下一轮不再碰它，只按 §5.4 盯那次 `abandoned` 的尝试。

### 5.4 取消之后厂商仍然完成的结果

**规则：不丢弃。下载、照实记费、留作可采用的一次，但不自动采用。**

理由：钱已经花了（本次实测一段 ¥7.5），把结果丢掉等于让用户白花钱；但用户明确说过「不等了」，之后可能已经改了提示词重出，自动采用会覆盖他现在的选择。

出片线程（`runner.py`）每一轮在处理完在跑的段之后，盯所有 `abandoned` 的尝试（按 `billing` 快照里的厂商去查）：

| 厂商给出的结果 | 处理 |
|---|---|
| 还在排队 / 生成 | 下一轮再查 |
| 成功 | 下载并检查可播放 → 尝试变 `succeeded` + `late: true`，按快照算出的实际费用记进 `spent_cny`；**不改 `chosen`，不改段状态**。挂靠到某一段的自由节点，结果照常复制进目标段（同样不自动采用） |
| 失败 | 尝试变 `failed`，厂商的错误照实记；有费用照记 |
| 已取消 | 尝试变 `cancelled` |
| 下载失败 / 文件不可播放 | 尝试变 `failed`，费用照记 |
| 查询一直出错 | 从第一次出错起满 `abandoned_give_up_sec`（默认 3600 秒）后放弃：尝试变 `failed`，错误 `film.cancel.lost`（「已取消的这一次一直查不到结果，无法确认是否计费」） |

用户看到的：

- 片段卡上一行小字「有取消后才出的结果，可以切换采用」，尝试切换器里能翻到它；侧栏尝试表里这一行标「取消后才出的结果」，可播放、可设为采用。
- 任务列表里一条「取消后仍生成完成」，注明「服务商已计费 ¥x」；同时发通知（§8.3）。

**预算**：`abandoned` 的尝试在有结果之前，按快照里的预估计入预留（`reserved`），算进上限——否则用户取消后立刻重出，可能两次都成功、合计超出上限。有结果后预留释放，按实际费用进 `spent_cny`。

**其它约束**：

- `abandoned` 的尝试**不算在跑**：不挡改设置、不挡重出、不挡合成。
- 自由节点还有 `abandoned` 尝试没结果时不能删（`film.free.pending_delete`：「这个节点有一次已取消的生成还没有结果，等它结束再删」），否则结果回来没处落。
- 服务重启后的恢复（`recover`）把「还有 `abandoned` 尝试」也算作需要出片线程盯的会话。

## 6. 接口

都在 `backend/server/app.py`，都要登录（`novel_user`），都只认本人的小说。

### 6.1 取消

- `POST /novels/{nid}/chapters/{cid}/versions/{vid}/render/clips/{clip_id}/cancel`
- `POST /novels/{nid}/chapters/{cid}/versions/{vid}/render/free/{fid}/cancel`

无请求体。成功返回会话视图外加 `cancel_outcome`（§5.1）。不能取消返回 409（§5.2）；会话或段不存在 404。

### 6.2 本人的出片任务

`GET /render/tasks` → `{ tasks: [...] }`。出片与合成任务都从它来（转换任务见 §8.5）。

返回四类：

1. 在排队 / 生成 / 取回的段与自由节点；
2. 一天（86400 秒）内结束的段与自由节点（靠 `ended_at` / `ended_as`）；
3. 一天内「取消后才出结果」的尝试（`late`）；
4. 成片合成：合成中的，或一天内结束的（一个版本一条，取会话里 `final` 的状态）。

已结束的按结束时间倒序，最多返回 30 条。

每项字段：

| 字段 | 说明 |
|---|---|
| `id` | `<版本>:<段或节点 id>`；`late` 的再加 `:<任务号>`（同一段可能既有「已取消」又有「取消后仍生成完成」两条）；合成是 `<版本>:compose` |
| `item_id`、`kind` | 段或自由节点的 id（合成为 `compose`）；`clip` / `free` / `compose` |
| `novel_id`、`chapter_id`、`version_id` | 定位与跳转 |
| `work_title`、`chapter` | 小说名、章节名：**每次请求现读**，改名后跟着变；读不到为 `null`（界面写「已删除」） |
| `shot_ids` | 这一段含哪些镜头（自由节点为它挂靠的那一段的；合成为空数组） |
| `cancel` | 现在能怎么取消：`free`（还没提交）/ `paid`（已提交）/ `null`（不能取消；合成恒为 `null`） |
| `error` | 失败原因（消息对象 `{code, params, message}`）；不能给普通用户看的为 `null`（§8.5） |
| `step` | 合成的当前步骤（消息对象）；其它为 `null` |
| `state` | `queued` / `running` / `downloading` / `done` / `failed` / `cancelled` / `late` |
| `elapsed_sec` | **服务端算的**已等秒数（结束的为总共等了多久）；不让浏览器拿自己的时钟去减服务器时间 |
| `typical_sec` | `[下限, 上限]`；合成为 `null` |
| `ended_at` | 在跑的为 `null` |
| `cost_cny` | 只有 `late` 有 |

**不返回厂商、模型、分辨率**。在跑的排前面，结束的按结束时间倒序。

**扫描范围**：不遍历用户的所有章节。只读两类会话：出片线程正在盯的（内存里的 `watching()` 集合，按路径归属筛出本人的），以及 `session.json` 一天内改过的（按文件修改时间）。任何让段进入或离开在跑状态的操作都会写文件，所以这两类合起来不会漏；代价是一次目录通配（`*/chapters/*/render/*/session.json`）加几个 `stat`，对单用户的量级可以接受。

读到的每个会话再核对一次 `owner.user_id`，不是本人的不返回。章节或小说被删后，它的会话目录随之消失，这些任务自然不再出现（不报错）。

## 7. 画布上的交互

### 7.1 等待一行

片段卡与自由节点卡在跑时，封面下方多一行（`WaitRow`）：

- 一般：`已等 2 分 05 秒 · 通常 3–7 分钟`
- 超过上限：`已等 8 分 20 秒 · 比通常久，仍在处理`
- 没有通常时长：`已等 2 分 05 秒`

每秒走一次。右端是取消入口。卡片头部的状态药丸回到只显示状态名（「排队中」「生成中」「取回中」），已等时间不再挤在药丸里。

侧栏「出片」页选中一段时，详情顶部有同样的一行。

时间轴视图的「成片」泳道文字不变（「生成中 · 已等 1:05」），那里空间只够这么多。

### 7.2 取消入口的两种写法

| 这一段现在 | 按钮文字 | 种类 |
|---|---|---|
| `queued` 且还没提交 | 取消 | 不花钱 |
| `running`（已提交，有任务号） | 不等了 | 可能已计费 |
| `queued` 正在提交（几秒的窗口） | 不显示（此时后端也会拒绝，§5.2） | — |
| `downloading` | 不显示（马上就好） | — |

种类只决定确认框的说法；真正的结局以后端返回的 `cancel_outcome` 为准（比如显示「不等了」但厂商其实还在排队，会得到 `cancelled`，提示「已取消，服务商没有扣费」）。

### 7.3 确认框

一律先确认（`useConfirm`）。

**还没提交：**

> 取消 E01-C01？
> 还没有提交给生成服务，现在取消不花钱。
> ［取消］［取消生成］

**已提交：**

> 不等 E01-C01 了？
> 这一段已经提交给生成服务。我们会先尝试取消；取消不了的话，**服务商可能仍会生成并扣费**——结果会留在这一段的尝试记录里，之后还可以采用。
> ［取消］［不等了］（危险色）

确认后按结局给一条提示：

| 结局 | 提示 |
|---|---|
| `dequeued` | 已取消，没有花钱 |
| `cancelled` | 已取消，服务商没有扣费 |
| `abandoned` | 已停止等待。服务商如果仍然生成完成会照常扣费，结果会留在尝试记录里 |

被拒（409）时错误走现有的出片错误条，并重读会话。

### 7.4 播放

- **片段卡 / 自由节点卡**：有结果时封面正中一个圆角的「▶ 播放」按钮（半透明黑底白字，始终可见，不靠悬停）。悬停时的静音循环预览保留。
- **侧栏「出片」页**：选中段的详情顶部一个「播放」按钮。尝试表里原有的小字「播放」链接不变（它在侧栏里内嵌播放）。
- 点开的是**播放窗口**（`ClipPlayer`，新组件）：对话框里一个 `<video controls autoPlay playsInline>`，不静音、不循环；标题「E01-C01 · 第 2 次」，是迟到结果的再标「取消后才出的结果」。文件走 `useFilm` 现有的 blob 缓存（和封面、侧栏小播放器是同一份，不重复下载）。
- 播哪一次：点名第几次就播那次；否则播采用的那次；没有采用就播最近成功的一次。

选择新做一个播放窗口而不是复用时间轴的预览窗：预览窗跟着播放头走、叠字幕、可能在播关键帧，语义是「预演整章」；这里要的是「看这一段出成什么样」。视频元素本身的样式类（`film__video`）是复用的。

## 8. 任务列表与通知

### 8.1 巡检

`App.tsx` 在转换任务的巡检旁边并排加一个出片任务的巡检（`watchFilm`）：

- 登录后立刻取一轮；
- 有在跑的 5 秒一轮，没有 15 秒一轮；
- 画布上发起生成或取消成功后立刻再取一次（`filmTasks.ts` 里一个极小的发布订阅 `pokeFilmTasks`），不必等下一轮；
- 助手发起出片（`onTask` 的 `kind: 'film'`）同样立刻取。

转换任务那一套（`watchJobs`、`announce`、`recentDone`）不动。

### 8.2 铃铛与动态面板

- 铃铛上的数字 = 在跑的转换任务数 + 在跑的出片任务数。
- 动态面板「在跑」区：每条写「小说 · 章节 · 片段」、状态药丸、「已等… · 通常…」、一个「查看」按钮。等待时间 = 服务端给的 `elapsed_sec` + 取回之后过去的时间，每秒走。
- 「最近完成」区：每条写名字与结局药丸（已生成 / 生成失败 / 已取消 / 取消后仍生成完成）；迟到的那种再加一行「服务商已计费 ¥x，可在片段里采用」。整条可点。
- 已结束的列表来自服务端（保留一天），刷新页面不丢。

（本节是只看出片片段时的样子；合成、转换并进来之后面板的完整结构见 §8.5。）

### 8.3 播报

每条结束的任务播报一次：桌面通知（`notify.ts`）加页内提示（sonner）。

| 结局 | 通知标题 | 页内提示的按钮 |
|---|---|---|
| 已生成 | 片段已生成 | 播放 |
| 失败 | 片段生成失败 | 查看 |
| 取消后仍生成完成 | 已取消的片段仍生成完成（正文带已计费金额） | 播放 |
| 已取消（用户自己点的） | **不播报** | — |

规则：

- 去重键是「任务 id + 结束时间」：同一段再出一次、再结束，照常播报。
- **登录后的第一轮只记账不播报**——刷新页面不该把十分钟内的结果再弹一遍。
- `notify()` 新增可选的 `tag` 与 `onClick`：出片按任务给 tag，几段同时完成不会互相顶掉；点通知先把窗口拉到前面，再执行回调。
- 通知权限：发起花钱的出片操作时顺手申请（`primeNotifications()`，和转换一致——借用户的这次点击）。
- 通知与提示里只有小说、章节、片段，没有厂商名。

### 8.4 点回画布（片段与自由节点）

点任务、点提示的按钮、点通知，走同一个函数 `openFilmTask(task, play)`：

- 目标地址：那一章的画布、节点图视图（`…/chapters/{cid}/render/canvas?view=graph`），侧栏停在「出片」页。
- 要选中谁放在**路由 state** 的 `focus` 里：`{ vid, id, play, taskId? }`。跟现有的 `panel: 'film'` 一样随这条历史记录走；导航被「未保存修改」拦下时，state 根本到不了，不会留下悬空的请求。
- 三种情形：
  - 别的章节：导航过去，版本号作一次性 state（现有机制，章节加载时打开那一版）；
  - 同一章、别的版本：先过未保存确认，换到那一版，再到画布；
  - 已经在那个地址：不导航，只把 `focus` 写进当前这条历史记录（replace）。
- 画布（`TimelineCanvas`）收到 `focus`：只认 `vid` 等于自己这一版的；等出片会话读到后执行一次——选中那一段、侧栏切到「出片」、`play` 为真就打开播放窗口（`taskId` 有值时播那个任务出的那一次，用于迟到结果）；然后回报，应用把 `focus` 从 state 里清掉（刷新、后退不会再播一次）。找不到那一段（比如已删的自由节点）时什么都不选，请求照样用掉。
- 结局与「是否播放」的对应：已生成、取消后仍生成完成 → 播放；在跑、失败、已取消 → 只选中。

### 8.5 统一的个人任务队列

用户要的是「全局看到目前有哪些任务在跑、进度如何、哪些结束了」。入口就是现有的任务铃铛：它在产品外壳里，任何页面（书架、小说页、章节、画布）都能点开；铃铛上的数字是**所有类型**进行中任务的总数。面板（`components/shell/ActivityPanel.tsx`）改成一个队列、两个区。

**逐类查清的结果**

| 任务类型 | 是不是异步 | 状态从哪来 | 进度怎么表示 | 能取消吗 | 已结束保留 |
|---|---|---|---|---|---|
| 小说转分镜（转换） | 是，后台线程，分钟级 | `GET /jobs`（进程内存里的任务表） | **百分比进度条**（已完成字数 / 总字数）+ 预计剩余时间（服务端按已完成字数外推）+ 最近一条进度事件 | 不能（后端没有中止机制；非目标） | 内存任务表在进程存活期间一直在；服务重启后清空（产物已落成版本，不丢） |
| 出片片段 / 自由节点 | 是，出片线程 | `GET /render/tasks` | **已等时长 + 通常区间**（厂商不给百分比） | 能，规则同 §5 | 一天 |
| 成片合成（配音 + 混音 + 拼接） | 是，后台线程 | `GET /render/tasks`（会话里的 `final`） | **当前步骤的文字**（合成线程每进一步写一次）+ 已等时长；没有百分比，也没有可靠的通常时长 | 不能（后端没有中止机制；非目标） | 一天 |
| 关键帧出图 | **不是任务**：`POST /render/keyframes` 同步返回每镜的出图提示词，图是用户自己上传的（`PUT …/keyframes/{shot}`） | — | — | — | — |
| 导出（`export.zip`） | **不是任务**：同步下载 | — | — | — | — |
| 章后整理（digest） | 是，但它是转换之后自动跑的一次小调用，不由用户发起 | 章节上的 `digest.status` | 不进队列（小说页已有自己的提示）| — | — |

**为什么不把转换也并进一个聚合接口**：转换任务活在 `app.py` 的进程内存里，前端围绕 `/jobs` 已经有一整套行为（任务面板的附着、跑完自动打开产物、书架与侧栏的在跑标记、3 秒 / 10 秒的轮询）。再造一个聚合接口要么让这些逻辑改吃新接口（大改、风险高），要么同一份数据拉两遍。所以数据来源保持两个，**在面板这一层合成一个队列**；用户看到的是一个列表。两个接口都只返回本人的任务（`/jobs` 按 `user_id` 过滤，`/render/tasks` 见 §6.2）。

**`GET /jobs` 的补充**（每条新增）：

- `finished_at`：结束时间（转换结束时记下，不论成败）；
- `error_msg`：失败原因，规则同下面的「失败原因」；
- `work_title`、`chapter` 改为现读的名字，读不到（小说或章节已删）时留提交时的名字，并标 `deleted: true`。

**面板的两个区**

- **进行中**：先列转换任务（进度条、预计剩余、最近一条进度），再列出片与合成任务（状态药丸、「已等… · 通常…」或「已等…」加步骤）。每条有「查看」；出片任务在 `cancel` 非空时多一个「取消」/「不等了」。
- **已结束**：转换、出片、合成混在一起按结束时间倒序，**最多 20 条**；每条有结局药丸、结束时间（当天写时分，隔天带月日，本地时间）、失败时的原因；整条可点（成功的片段点开即播放，其余是查看）。
- 都没有时是原来的空状态。

**保留多久**：出片与合成任务服务端保留一天、最多返回 30 条；转换任务取 `/jobs` 里所有已结束且带结束时间的（服务重启即清空），与应用自己记下的「刚结束」合并去重；面板最终只显示最新的 20 条。

**失败原因**：给用户可读的文案（消息对象，按界面语言渲染）。但现有的错误消息里有一部分带厂商原话或厂商名（§10.1），不能出现在这个面板里。所以两个接口都过一道筛子（`_public_error`）：消息参数里有厂商原话（`vendor(...)` 包过的值）、或文字里出现厂商名 / 模型名（固定词表加这个会话的厂商与模型）的，一律返回 `null`；面板这时写「点开查看原因」，原因在任务所在的页面看。合成的步骤文字过同一道筛子。

**面板里取消**：点「取消」/「不等了」弹的确认框与画布上是同一套文案（§7.3）；确认后直接调取消接口，按结局提示，然后让任务列表与开着的画布各自重读。接口返回 409（比如刚好跑完）时提示错误文案并重读列表。

**播报**：合成完成 / 失败也各播报一次（「成片已合成」「成片合成失败」），规则同 §8.3。转换任务的播报不变。

**刷新方式**：沿用轮询，两条线各自降频。

| 来源 | 有进行中的 | 没有进行中的 | 立刻再取的时机 |
|---|---|---|---|
| `/jobs`（转换） | 3 秒 | 10 秒 | 提交转换后；助手发起转换后 |
| `/render/tasks`（出片、合成） | 5 秒 | 15 秒 | 画布上发起生成或取消后；面板里取消后；助手发起出片后 |

面板开着时，进行中条目的「已等」每秒在本地走一次（以服务端给的秒数为起点），不额外请求。

### 8.6 每条任务的定位

队列是全局的，所以每条的第一行是它在哪：

| 任务类型 | 定位行 | 例 |
|---|---|---|
| 出片片段 | 小说 › 章节 › 片段号 · 所含镜号范围 | `药 › 第一章 › E01-C01 · SH001–SH003` |
| 自由节点 | 小说 › 章节 › 节点号（挂靠到某一段时带那一段的镜号范围） | `药 › 第一章 › F01` |
| 成片合成 | 小说 › 章节 › 成片合成 | `药 › 第一章 › 成片合成` |
| 转换 | 小说 › 章节 | `药 › 第一章` |

- **镜号范围**：取 `shot_ids` 的第一个和最后一个的短镜号（去掉集前缀），只有一个镜头不写范围。一段里的镜头本来就是连续的。
- **版本与集**：片段号本身带集（`E01-…`）。版本不显示在定位行里（版本号是内部 id，对用户没有含义），但跳转时用它打开正确的那一版。
- **名字取当前值**：服务端每次请求现读小说名、章节名，改名后下一轮轮询队列就跟着变。
- **已删除**：出片与合成任务所在的章节 / 小说被删，会话目录一起没了，任务从队列里消失；万一名字读不到，那一段写「已删除」占位。转换任务活在内存里，删了小说或章节它还在：留提交时的名字，后面标「（已删除）」。点它会走现有的「小说 / 章节已不存在」提示并回到上一级，不报错。
- **窄屏**：定位行单行、超长截断（省略号），`title` 属性是全称，悬停可见。

**点击跳到哪**（复用现有路由，不新增地址）：

| 任务类型 | 去处 | 用的机制 |
|---|---|---|
| 出片片段 / 自由节点 | 小说 → 章节 → 画布节点图，选中那一段，侧栏停在「出片」页；成功的顺便播放 | §8.4：`chapterPath(nid, cid, { step, canvas: true, view: 'graph' })` 加路由 state 的 `vid`（打开那一版）、`panel: 'film'`、`focus` |
| 成片合成 | 小说 → 章节 → 画布（时间轴），侧栏停在「出片」页（合成区与成片在那里） | 同一个函数，不带 `focus`、不带 `view` |
| 转换（进行中） | 那一章，接上任务面板 | 现有的 `openJob` → `openChapter(cid, nid, jobId)` |
| 转换（已结束） | 成功：打开它产出的那一版；失败：接上任务面板看原因 | 现有的 `openFromToast` |

画布里现有的「跳回某个镜头」（`onJumpShot`）是从画布回分镜页用的，方向相反，这里不用；从队列到画布上的片段用的是 §8.4 新加的 `focus`。定位到的是片段（一段含若干镜头），选中片段后侧栏「出片」页里列着它的每个镜头，可以再点到具体镜头。

## 10. 疑点与后续

### 10.1 现有界面已经在向普通用户暴露厂商名（超出本次范围）

本次只保证新增内容不带。现有的这些地方仍然带，建议另开一件事处理：

- 侧栏「出片」页的设置区：厂商与档位的下拉、设置摘要一行；
- `film.panel.defaultNote` 等文案，以及后端若干错误消息（如「视频服务（MiniMax）…」）；
- 花钱确认框里的费率说明（`rate_note`）与厂商控制台名（`console.*`）；
- 会话视图把尝试里的 `billing`（含厂商、模型）原样下发给浏览器——界面不显示，但在网络响应里。

### 10.2 会话视图把带签名的 `video_url` 下发给浏览器

`view()` 现在把尝试对象原样返回，其中有厂商给的带签名下载地址。界面不用它（文件走我们自己的 `/files`）。这是既有问题，本次未动，建议在清理 §10.1 时一并从视图里剔掉。

### 10.3 Seedance 的通常时长没有实测

(120, 480) 是保守估计。它只影响界面上「通常 x–y 分钟」的数字，实测后改一个常量即可。

### 10.4 「正在提交」时取消返回 409

见 §5.2。窗口很短；如果实际使用中用户常点到，再考虑做成「标记待取消，提交返回后自动取消」。

### 10.5 任务列表的扫描依赖文件修改时间

见 §6.2。如果以后会话改成不落文件（比如进数据库），这里要跟着换成查询。

### 10.6 转换任务的已结束列表不跨服务重启

转换任务的状态在进程内存里，服务重启后 `/jobs` 是空的，队列里就看不到重启前结束的转换（产物本身已落成版本，在章节的版本列表里）。要跨重启保留，得把任务摘要落盘或从版本记录反推，这次没做。

### 10.7 转换与合成不能取消

两者都是后台线程里一口气跑完的，没有检查点。队列里它们没有取消入口。要支持需要在各自的执行循环里加中止标记，另开一件事。

### 10.8 失败原因的筛子是词表

`_public_error` 靠 `vendor(...)` 标记加一份厂商词表判断。新接厂商时要记得往词表里加名字；更彻底的办法是 §10.1 的清理（让错误消息本身就不带厂商名）。

### 10.9 `film.test.tsx` 偶发卡死（既有）

`frontend/tests/film.test.tsx` 在本次改动之前就会偶发 CPU 自旋不退出（并行压测基线 6 次里 2 次，改动后的副本 6 次里 0 次，与本次改动无关）。计划的全局约束里写了遇到时如何单独重跑判定。值得单独查一次根因。
