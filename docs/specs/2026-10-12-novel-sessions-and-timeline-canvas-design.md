# 小说级会话管理 + 时间轴画布 设计

日期：2026-10-12 · 分支：langchain

## 1. 背景与目标

现状的问题：

- 每次转换是一条扁平的「转换记录」，与小说、章节的关系只靠 `work_title` / `chapter`
  两个自由字符串。作品名打错一个字就成了另一部小说。
- 章节之间没有结构关系：每章的句子编号都从 `u0001`、分集编号都从 `E01` 起；
  下一章不知道上一章发生过什么。
- 资产库按作品名分组（`library.json`），是唯一的跨章记忆，但它游离在转换记录之外。

目标：按 Agent 的会话模型重组。

| Agent 概念 | 本项目 | 记忆 |
|---|---|---|
| 用户实体（总会话） | **小说** | 长期记忆：资产库、制作参数、编号接续、人物生命周期、主线剧情、创作限制 |
| 一次提问（二级会话） | **章节** | 短期记忆：本章原文、各版本的转换过程（日志/尝试/修复/清单）与产物 |

用户新建一个总会话 = 开始一部新小说。

第二阶段在此结构上做**时间轴画布**：按视频时长铺开的无边界画布，播放头推进时用连线
串起镜头顺序与每个角色的动作顺序。

## 2. 实体与存储

沿用现有「一个 JSON 一个文件、按用户隔离、无数据库」的做法：

```
data/users/<uid>/novels/<nid>/
  novel.json                 小说本体 + 长期记忆
  chapters/<cid>/
    chapter.json             章节本体（标题、顺序、原文、采用版本）
    versions/<vid>.json      一次转换 = 现有 run 记录的形状（params/result/manifest/…）
```

### 2.1 小说（总会话）

```jsonc
{
  "id": "n_…", "title": "药", "created_at": "…", "updated_at": "…",
  "params": { /* ConvertParams 的小说级默认值：风格前缀、画幅、旁白模式、音色… */ },
  "memory": {
    "assets":    { "characters": [], "locations": [], "props": [], "creatures": [] },
    "numbering": { "next_unit": 133, "next_para": 28, "next_episode": 5 },
    "lifecycle": [ /* 见 §3 */ ],
    "plot": {                         /* 见 §4 */
      "outline": "……用户写的全书梗概（可空）……",
      "chapters": [ { "chapter_id": "c_…", "synopsis": "……", "origin": "model" | "user" } ]
    },
    "constraints": [ /* 见 §5 */ ]
  }
}
```

- `assets` 即现有 `library.json` 里该作品那一份，迁入后 `library.json` 退役。
- `numbering` 只由**采用版本**推进（§2.3），保证全书 ID 唯一：第 2 章从 `u0133`、`E05` 起。
- 章节可单独覆写参数（比如某章改旁白模式），覆写只存在该版本的 `params` 里。

### 2.2 章节（二级会话）

```jsonc
{
  "id": "c_…", "title": "第一章", "order": 1,
  "text": "……本章原文……",
  "adopted_version": "v_…",          // null = 还没有采用版
  "versions": ["v_…", "v_…"]         // 只存 id，按时间排；详情在 versions/
}
```

### 2.3 版本与「采用」

- 同一章每转换一次就多一个版本（换参数重转、对结果不满意重转）。版本记录就是
  现有 run 记录：`params`、`status`、`result`、`manifest`、`quality_report`、日志等，
  编辑、复验、渲染沿用现有逻辑。
- **只有采用版进入长期记忆**。采用一个版本时：
  1. 资产卡并回小说的资产库（现有 `import_assets` 的合并规则）；
  2. 推进 `numbering`（取该版本产物里最大的句子/段落/分集编号 +1）；
  3. 触发一次「章后整理」小调用（§3.2），同时产出人物生命周期提议与本章剧情摘要（§4）。
- 首个成功版本默认自动采用；之后用户可改采用另一版。
- **改采用版的限制**：如果后面的章节已经基于它的编号转换过，换采用版会让编号对不上。
  规则：只有「最后一个已采用的章节」可以换采用版；更早的章节要换，界面提示后续章节
  需要重转。长期记忆里的资产与生命周期按「谁写入的」打来源标记（章节 + 版本），换采用版
  时撤回旧版写入的那部分再写入新版的。

### 2.4 长期记忆如何进入下一章的转换

转换某章时，程序从小说取：

| 记忆 | 注入方式 | 现状 |
|---|---|---|
| 资产库 | 【已有资产库】（首批即带） | 已有，`seed_assets` |
| 编号接续 | 冻结句单元从 `next_unit`/`next_para` 起编；【续批参数】的起始分集取 `next_episode` | 新增：`build_frozen_units` 加起始偏移 |
| 制作参数 | 小说默认值 + 本章覆写 | 新增 |
| 人物生命周期 | 新增【人物状态】块（§3.3） | 新增 |
| 主线剧情 | 新增【主线剧情】块（§4.3），明确「只用于理解，不得据此出画面」 | 新增 |
| 创作限制 | 新增【创作限制】块 + 能确定性落地的直接写进产物（§5.3） | 新增 |

## 3. 人物生命周期

### 3.1 要记的事

主线人物的**不可逆**状态变化：

| 类型 | 例子 |
|---|---|
| `deceased` 死亡 | 华小栓病死 |
| `permanent_condition` 永久伤病/残疾 | 左腿残疾，此后行走需拐杖 |
| `departed` 永久下线 | 远走他乡，此后不再出场 |

暂时性的（受伤后痊愈、短暂离开）不记——那是章节内的事，由产物本身表达。

每条记录：

```jsonc
{
  "id": "l_…", "character_id": "C03", "type": "deceased",
  "detail": "病死",                         // permanent_condition 写具体情况
  "since": { "chapter_id": "c_…", "unit_ref": "u0121" },
  "evidence_quote": "……原文逐字摘录……",
  "origin": "model" | "user",
  "status": "proposed" | "confirmed" | "rejected",
  "written_by": { "chapter_id": "c_…", "version_id": "v_…" }
}
```

### 3.2 怎么来：模型提议 → 程序核证据 → 人确认

1. 采用一个版本后，用一次「章后整理」小调用（只给本章句单元 + 角色卡名单，不给整份产物）
   让模型列出本章发生的不可逆状态变化，每条必须给 `unit_ref` 和逐字 `evidence_quote`；
   同一次调用顺带产出本章剧情摘要（§4.2），不为摘要另花一次调用。
2. 程序核对：`evidence_quote` 必须是所引句单元原文的子串、`character_id` 必须在资产库里，
   不过的直接丢弃并记日志。——和全项目「证据由程序核验」的口径一致，模型编不出不存在的死亡。
3. 通过核对的进入 `proposed`，界面上逐条确认/驳回；用户也可以手动添加（`origin: user`）。
4. 只有 `confirmed` 的进入下一章的提示词。

成本：每章采用时一次小调用（输入约为本章原文长度，输出很短），生命周期与剧情摘要共用。
可以关（`STORYBOARD_CHAPTER_DIGEST=0`），关了就只能手动添加生命周期、手写摘要。

### 3.3 怎么用

- **注入**：转换后续章节时，用户消息加【人物状态】块，例如
  「C03 华小栓：第 2 章已死亡（u0121）。现实时间线的镜头不得让他出场；回忆、梦境、
  他人讲述的画面可以，须在 action 里写明是回忆。」
  永久伤病同理（「此后外貌与动作须体现：左腿残疾，拄拐」）。
- **核查**（软，不打回）：产物里已故/已下线角色出现在镜头的 `characters` 里，且该镜头
  `action`/`atmosphere` 不含「回忆」「梦」等标记 → 记一条 MEDIUM Finding，供人工审阅。
  不做硬失败：IR 没有「时间线」字段，程序判断不了是不是闪回。

## 4. 主线剧情

### 4.1 要记的事

两层：

- **全书梗概** `plot.outline`：用户在建小说时（或任何时候）手写，可空。适合已经读过全书、
  想让模型从第一章起就知道人物最终走向的情况。
- **逐章摘要** `plot.chapters[]`：每章采用后自动生成，可手改；按章节顺序累积成「主线」。

### 4.2 怎么来

- 逐章摘要由章后整理调用产出（§3.2），每章不超过 200 字，写人物、事件、因果，不写画面。
- 摘要**不做逐字核验**：它是概括不是证据，核验不了，也不拿它当任何镜头的依据（§4.3）。
  所以它只能进「理解用的上下文」，永远不进产物。
- 用户改过的摘要标 `origin: user`，之后不再被自动覆盖（换采用版时也不覆盖，只提示）。

### 4.3 怎么用，以及不越界

转换后续章节时加【主线剧情】块：全书梗概 + 此前各章摘要（按章节顺序）。
块首固定写明：

> 以下主线剧情只用于理解人物关系、称谓与来龙去脉。本章的每个镜头仍必须依据本章原文句子，
> 不得把主线剧情里有、本章原文里没有的情节画进镜头，也不得据此补写台词与旁白。

这条和忠实转换的核心主张一致：溯源校验本来就会拦下没有原文依据的镜头内容
（`derivation=explicit` 却引不到句子），所以即使模型越界，也会被现有的保真校验打回。

长度控制：注入总长上限 2000 字。超过时，最近 3 章保留完整摘要，更早的章节每章只保留首句；
全书梗概始终完整保留（它是用户写的，信息密度最高）。

## 5. 创作限制

### 5.1 要记的事

用户为整部小说定的规矩，例如「不出现血腥画面」「不出现吸烟镜头」「主角不露正脸」
「不出现现代物件」。每条：

```jsonc
{
  "id": "k_…",
  "text": "不出现血腥画面，暴力用侧面、遮挡或旁白交代",   // 给模型看的规则
  "negative_prompt": "血迹, 伤口特写, 血腥",              // 可选：直接进画面负面提示词
  "keywords": ["血", "伤口"],                              // 可选：程序扫描用
  "enabled": true
}
```

### 5.2 优先级：原文溯源 > 限制

限制约束的是**怎么呈现**，不能让原文句子消失。原文写了「鲜血淋漓」，这句仍要有镜头或旁白
承载（覆盖率不变），只是画面改成侧面、遮挡、空镜，或交给旁白。【创作限制】块里写明这一点，
否则模型可能为了守规矩而跳过句子，直接撞上覆盖率硬校验。

### 5.3 怎么落地（能确定性的不交给模型）

| 手段 | 做法 | 性质 |
|---|---|---|
| 提示词 | 【创作限制】块列出全部启用的 `text`，附 §5.2 的优先级说明 | 靠模型遵守 |
| 负面提示词 | 各条 `negative_prompt` 由程序并入产物的 `meta.style.negative_prompt`（与模型自己写的去重合并，在 `apply_meta_overrides` 同一处） | 确定性，渲染时生效 |
| 关键词扫描 | 在**呈现层字段**（`action`、`atmosphere`、`characters[].action`、`prompts`）里扫 `keywords`，命中记 MEDIUM Finding，指名镜头 | 软核查，不打回 |

关键词只扫呈现层：台词、旁白、原文句子是原文逐字，扫它们会把原文本身判成违规。
不做硬失败：关键词命中不等于违规（「血」也在「血色夕阳」里），交给人工审阅。

## 6. 接口

新增（旧的 `/convert`、`/history`、`/library` 在迁移完成、前端切换后删除）：

```
POST   /novels                                  建小说（标题 + 默认参数）
GET    /novels                                  我的小说列表（含章节数、最近更新）
GET    /novels/{nid}                            小说详情：参数、章节摘要、长期记忆
PATCH  /novels/{nid}                            改标题/默认参数
DELETE /novels/{nid}

POST   /novels/{nid}/chapters                   新建章节（标题、原文）
PATCH  /novels/{nid}/chapters/{cid}             改标题/原文/顺序（有采用版后原文锁定）
DELETE /novels/{nid}/chapters/{cid}

POST   /novels/{nid}/chapters/{cid}/versions    转换本章 → 返回 job_id（复用现有任务/进度/分批预览）
GET    /novels/{nid}/chapters/{cid}/versions/{vid}
PUT    /novels/{nid}/chapters/{cid}/versions/{vid}        人工编辑 + 整份复验（现有逻辑）
POST   /novels/{nid}/chapters/{cid}/versions/{vid}/adopt  采用（§2.3）

GET    /novels/{nid}/memory                     长期记忆
PUT    /novels/{nid}/memory/assets/{kind}/{id}  资产卡增改（现有资产库逻辑）
POST   /novels/{nid}/memory/lifecycle           手动添加
POST   /novels/{nid}/memory/lifecycle/{lid}     确认 / 驳回 / 修改
PUT    /novels/{nid}/memory/plot                全书梗概；PUT …/plot/chapters/{cid} 改某章摘要
POST   /novels/{nid}/memory/constraints         新增限制；PATCH/DELETE …/constraints/{kid}
```

`/jobs`、`/jobs/{id}`、`/jobs/{id}/partial` 不变；任务记录里加 `novel_id`/`chapter_id`/`version_id`。

## 7. 迁移

一次性、幂等的迁移脚本（启动时检测旧数据自动跑，原文件备份不删）：

- 旧转换记录按 `work_title` 归成小说、按 `chapter` 归成章节，每条记录成为一个版本；
  每章最近一次成功（含编辑过的）版本设为采用版。
- `library.json` 里同名作品的资产迁入对应小说的 `memory.assets`；没有转换记录的作品也建成小说（无章节）。
- 旧数据的编号本来就不连续（每章从 `u0001` 起），迁移后 `numbering` 从「已采用版本的最大编号 +1」起，
  只保证**以后**的章节接续；旧章节标记 `legacy_numbering: true`，不改写。
- 生命周期、主线剧情、创作限制为空，不对旧章节补跑章后整理（要的话界面上可以对某章手动触发）。

## 8. 前端导航

```
侧栏                          主区
├ 小说 A                      小说页：参数 / 主线剧情 / 创作限制 / 资产库 / 人物生命周期（待确认的提议高亮）
│  ├ 第一章  ✓采用 v2          章节页：原文 + 「转换」→ 任务面板（进度、分批预览）
│  ├ 第二章  转换中…                   版本切换条 v1 v2 v3（标出采用版）
│  └ ＋ 新章节                         产物：分镜 / 资产卡 / 原文溯源 / 渲染 / JSON / 画布
├ 小说 B
└ ＋ 新小说
```

- 现在顶栏的「资产库」页并入小说页。
- 「打开本地 JSON」保留，仍是不入库的离线审阅。

## 9. 时间轴画布（第二阶段）

### 9.1 定位

**只读的播放视图**，编辑仍在现有分镜页；但数据流按「将来在画布上编辑」预留（§7.4）。
它仍是 IR 的审阅器，不越界做剪辑——产品边界不变。

### 9.2 布局

无边界画布：全屏、无外框，可拖动平移、滚轮缩放；横轴是视频时间（按**可播时长**
累计，即 `max(duration_sec, 念完旁白台词所需)`，与渲染计价同一口径）。

```
时间  0s ──────── 30s ──────── 60s ──────── 90s ──▶   ▼ 播放头
集    [ E01 ………………………………………… ][ E02 ……………
场景  [ S01 茶馆 ][ S02 刑场 …………… ][ S01 茶馆 ]
镜头  [SH01][SH02][SH03 ……][SH04][SH05] …            ← 连线：镜头顺序
C01   ●推门──────●端碗────────────●坐下                ← 连线：该角色的动作顺序
C02         ●咳嗽───────●按胸
旁白  ▂▂▂▂      ▂▂▂▂▂▂            （台词/旁白段，悬停看原文）
BGM   ～～～ 压抑 ～～～ 紧张 ～～～                     （music.curve 情绪段）
```

- 每个角色一条泳道：该角色出场的镜头处画一个节点，标 `characters[].action`
  （没有就退回镜头 `action`），悬停看表情、位置、服装。
- **播放头推进**：按真实时间（可 0.5×/1×/2×）或拖动；播放头经过的部分，镜头连线和
  各角色的动作连线逐段点亮，当前镜头高亮并在侧边浮层展开详情（画面描述、台词、旁白、原文句）。
- 点镜头节点跳到分镜页对应镜头；点原文句跳到原文溯源页。

### 9.3 技术

- 自绘 SVG + CSS transform 做平移缩放，不引入画布库（现在前端零运行时依赖，只有 react）。
- 布局计算（时间 → 横坐标、泳道分配、连线）放纯函数模块 `timeline.ts`，单测覆盖；
  渲染组件只吃计算结果。
- 一章 100+ 镜头、十几条泳道的规模，SVG 足够；超过再考虑虚拟化。

### 9.4 为编辑预留

- 画布上的任何改动都表达成**操作**（`setDuration(shotId, sec)`、`setCharacterAction(…)`），
  走现有 `edit.ts` 的同一套函数，锁定字段的规则（原文、溯源、ID 不可改）自动沿用；
  保存仍走 `PUT …/versions/{vid}` 整份复验。
- 第一版只读：操作层建好、单测覆盖，但画布不暴露编辑手势。
- 镜头**顺序**原则上不开放拖动：ORDER-001 不许讲述回跳，能合法挪动的空间很小。

## 10. 实施顺序

| 阶段 | 内容 | 可独立交付 |
|---|---|---|
| 1 | 存储层（novel/chapter/version）+ 迁移 + 新接口，旧接口暂留 | 后端测试全绿，旧前端仍可用 |
| 2 | 长期记忆接入转换：编号接续、小说级参数、资产库 | 续写第二章编号接续、角色不漂移 |
| 3 | 章后整理：人物生命周期（提取、核证据、确认、注入、软核查）+ 逐章剧情摘要；主线剧情与创作限制的注入、负面提示词落地、关键词扫描 | 实跑：一章含人物死亡、一条「不出现血腥」限制 |
| 4 | 前端导航改为 小说 → 章节 → 版本；删除旧接口 | 端到端界面测试覆盖 |
| 5 | 时间轴画布（只读 + 操作层） | 界面测试 + `timeline.ts` 单测 |

## 11. 待确认 / 风险

- **生命周期提取的准确度**：弱模型可能漏报（比如死亡写得隐晦），所以有手动添加；
  误报靠「必须给原文逐字证据 + 人确认」兜住。
- **主线剧情会不会诱导模型越界出画面**：§4.3 的声明 + 现有溯源校验兜底；实跑时专门看
  inferred 镜头比例有没有上升。
- **限制与原文冲突**：§5.2 规定原文优先；若某条限制让模型频繁漏句（覆盖率硬失败增多），
  说明这条限制写法有问题，界面上要能看出是哪条限制在起作用。
- **改采用版的级联**（§2.3）：限制为只有最后一章可自由换，是为了不让编号接续出错；
  如果你常常回头重转早期章节，这条限制会碍事，需要另想办法（比如编号按章节分段预留）。
- **画布的「无边框」**：我理解为全屏、无外框、可无限平移缩放的画布。如果你指的是
  别的样式（比如嵌在页面里但不画边框），第 5 阶段开工前再对一下。
