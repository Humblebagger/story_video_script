# 运营后台结构与外观改造设计

日期：2026-11-21　分支：langchain　状态：待设计审查

上一份后台设计：`docs/specs/2026-10-29-admin-console-design.md`（功能与接口以它为准，本文只改外框与排版）。

## 1. 背景与目标

对比一个竞品的运营后台后，结论是我们的后台「像 demo」：六个页签挤在一排按钮里，只有一个地址 `/admin`，刷新就回到概览；概览是六个光秃秃的数字，看完不知道下一步去哪；各页的标题、刷新按钮、空状态各写各的。

竞品值得学的只有结构与外观：左侧分组导航；总览是带副标题和「去处理 →」链接的数字卡片；小卡片列分布；一张近 14 天趋势图；干净的白底卡片。

目标（用户已确认，选的是「只做结构与外观」）：

1. 外框换成「左侧分组导航 + 右侧内容」，每页有自己的地址，刷新与后退可回。
2. 总览页改成带副标题与行动链接的数字卡片，加近 14 天趋势图与分布小卡片。
3. 其余五页统一标题行、表格、空 / 加载 / 错误的样子，功能不变。

## 2. 范围与非目标

范围：**纯前端**。不新增后端接口，不改后端任何文件，只用 `frontend/src/api.ts` 里现有的 `admin*` 函数。

非目标（本次不做）：

- 兑换码、客服、公告等新模块。
- 新的后端接口、新的统计口径。**现有接口给不出的数字一律不显示**（逐项决定见 §5.4）。
- 用户页的筛选（按状态、按角色）、列表分页、导出。
- 产品外壳（`AppShell`）的改动。
- 后台的权限模型：仍然是「角色为 admin 才能进，权限以后端为准」。

不变的约束：普通用户界面不得出现模型名或供应商名；后台是管理员页，模型名照旧显示（用量页、用户详情、概览的未定价提醒与按模型分布）。

## 3. 外框

### 3.1 后台独立成一屏

现在后台渲染在产品外壳 `AppShell` 的内容区里（左边是产品侧栏，上面是产品顶栏）。改造后**在后台时不渲染 `AppShell`，后台自己占满一屏**：

```
┌────────────┬──────────────────────────────────────────┐
│ 运营后台 ⇤ │  页名                          [操作…]   │
│ ← 返回产品 │                                          │
│            │  （页面内容）                            │
│ 总览       │                                          │
│  运营概览  │                                          │
│ 用户与用量 │                                          │
│  用户      │                                          │
│  用量与花费①│                                         │
│ 运行       │                                          │
│  任务 ③    │                                          │
│  错误 ②    │                                          │
│  审计      │                                          │
│            │                                          │
│ 🌐 ◐ root  │                                          │
└────────────┴──────────────────────────────────────────┘
```

理由：套在产品外壳里会出现两条侧栏，也放不下「运营后台」标题与返回链接；独立一屏的改动反而最小 —— `AppShell` 一行不用动，`App.tsx` 只是在「当前地址是后台且用户是管理员」时渲染 `AdminView`，否则照旧渲染 `AppShell`。

代价：后台里没有产品顶栏，所以语言切换、主题切换要放进后台自己的导航底部（复用现成的 `LangToggle`、`ThemeToggle`），旁边显示当前用户名。任务铃铛、打开本地 JSON、助手入口在后台里不出现（它们是产品功能）；退出登录回产品里做。

### 3.2 导航

三个分组、六项，顺序固定：

| 分组 | 导航项 | 地址 | 对应原页签 |
| --- | --- | --- | --- |
| 总览 | 运营概览 | `/admin` | 概览 |
| 用户与用量 | 用户 | `/admin/users` | 用户 |
| 用户与用量 | 用量与花费 | `/admin/usage` | 用量 |
| 运行 | 任务 | `/admin/jobs` | 任务 |
| 运行 | 错误 | `/admin/errors` | 错误记录 |
| 运行 | 审计 | `/admin/audit` | 审计 |

- 左上角是标题「运营后台」（英文沿用 Admin console）和「返回产品」按钮（英文 Back to app）。
- 每个导航项是**真链接**（`<a href>`），可以在新标签页打开；普通左键点击走前端路由，不整页刷新。当前页高亮并带 `aria-current="page"`。
- **可收起**：点标题旁的按钮收成只有图标的窄条，图标带 `title` 与 `aria-label`；计数徽标缩小后仍然显示。收起状态记在 `localStorage`（键 `inkreel.admin.navCollapsed`），读写失败就只在本次有效。
- **窄屏（宽度 < 768px）**：没有侧栏，顶部一条：返回按钮、标题、一个原生下拉框（按三个分组分 `optgroup`）、语言与主题切换。计数写在选项文字里，如「任务（3）」。跟着窗口宽度变化实时切换。

### 3.3 导航项旁的计数

只显示现有接口能给出的数，为 0 或数据没到就不显示徽标；超过 99 显示「99+」。

| 导航项 | 数字 | 来源 | 徽标说明文字 |
| --- | --- | --- | --- |
| 任务 | 近 7 天失败的任务数 | `GET /admin/overview` 的 `failed_7d` | 近 7 天失败 N 个 |
| 用量与花费 | 未定价的模型数 | `GET /admin/overview` 的 `unpriced_models.length` | N 个模型未定价 |
| 错误 | 近 7 天的错误记录数 | `GET /admin/errors` 列表里 `at` 在 7 天内的条数 | 近 7 天 N 条错误记录 |

说明与取舍：

- 后台没有「已处理 / 未处理」的概念，所以这些数严格说是「近期需要看一眼的量」，不是待办数。徽标的 `title` 写明口径，不写「待处理」。
- 错误列表接口最多返回最近 200 条；如果近 7 天超过 200 条，数到的是 200，显示成「99+」，不影响含义。
- 「未定价的模型数」用提醒色（黄），另外两个用警示色（红）。
- 用户、运营概览、审计没有计数（没有合适的现有数字）。
- 数据获取：外框取一次 `adminOverview`（每 30 秒刷新）和一次 `adminErrors`（每 60 秒刷新）。外框把同一份概览数据传给概览页，**概览页不再自己重复请求**；概览接口失败时导航照常可用，只是没有来自它的两个计数。

### 3.4 地址

| 地址 | 含义 |
| --- | --- |
| `/admin` | 运营概览 |
| `/admin/users`、`/admin/usage`、`/admin/jobs`、`/admin/errors`、`/admin/audit` | 各页 |
| `/admin/jobs?state=running` \| `?state=failed` | 任务页只看运行中 / 只看失败；不带参数是全部 |
| `/admin/usage?group=day\|model`、`?days=7\|90` | 用量页的分组与天数；缺省是按用户、30 天 |

规则（沿用 `docs/specs/2026-11-12-frontend-routing-design.md` 的做法：一条通配路由，`paths.ts` 的 `parseLocation` 解析，不规范的地址 `replace` 到规范地址）：

- 规范地址由新函数 `adminPath(page, { state, group, days })` 拼出，缺省值不写进地址；参数顺序固定为 `group` 在前、`days` 在后。
- `/admin/overview`、`/admin/`、非法的参数值、别的页带了不认识的参数、参数乱序，都 `replace` 到规范地址。
- `/admin/<不存在的页>`、`/admin/users/<更深的路径>` 是 404 页。
- `Loc` 的后台分支从 `{ kind: 'admin' }` 扩成 `{ kind: 'admin'; page; state; group; days }`。`App.tsx` 里所有 `loc.kind === 'admin'` 的判断（管理员守卫、未登录弹登录框、标题）不用改逻辑。
- **导航换页是 push**（后退能回到上一页）；**改筛选是 replace**（后退直接离开这一页，和分镜视图切页签的做法一致）。
- **刷新**：地址就是全部状态，刷新后回到同一页同一筛选。
- **返回产品**：后台内部翻页会留下历史，不能再用「后退一步」。`App.tsx` 记住进后台之前在产品里的最后一个地址（连同是哪个用户的），点「返回产品」跳回那里；直接从后台地址打开（没有之前的地址）或换过账号就回首页 `/`。
- 浏览器标题：`<页名> · 运营后台 — Inkreel`。
- 非管理员打开任何后台地址：和现在一样回首页并提示「需要管理员权限」。

## 4. 各页的统一样式

### 4.1 标题行

每页最上面一行：左边是页名（与导航项同名，`h2`），右边是这一页的操作。加载中、读取失败时标题行也在（现在有几页读取失败时整页只剩一条错误）。

| 页 | 标题行右侧 | 标题行下面 |
| --- | --- | --- |
| 运营概览 | 刷新 | 一行说明「金额按当前价格表估算。」在页名下方 |
| 用户 | 刷新（新增；原来没有） | 搜索框 |
| 用量与花费 | 导出 CSV、刷新 | 分组、天数两个分段控件 |
| 任务 | 筛选（全部 / 运行中 / 失败）、刷新 | 两张表 |
| 错误 | 刷新 | 按参考编号查找的表单 |
| 审计 | 刷新 | 表 |

### 4.2 表格、空状态、加载、错误

- 表格沿用现有的 `.adm__table`（卡片底、细分隔线、`is-num` 列右对齐等宽数字），表头不折行。不重写表格。
- 空状态统一成一个组件 `Empty`（放在已有的 `LoadState.tsx`）：收件箱图标 + 一句话 + 可选说明，带和表格一样的卡片底。五处原来各自拼 `EmptyState` 的地方都换成它。
- 加载：沿用 `TableSkeleton`；概览页是卡片形状的骨架。
- 错误：沿用 `ErrorBar`（文字按语言渲染、带重试），加上卡片底。

### 4.3 各页功能不变，只有两处为地址服务的最小改动

- **任务页**：加筛选。组件接受可选的 `state`（`'running' | 'failed' | null`）与 `onState`；外框把地址里的 `state` 传进来，点筛选时回调，由上层改地址。不传这两个属性时筛选是组件内状态（单独渲染、现有测试的用法不变）。「运行中」只显示运行中那张表，「失败」只显示近 7 天失败那张表，「全部」两张都显示（即现在的样子）。
- **用量页**：分组与天数接受可选的 `group`、`days`、`onQuery`，规则同上。

用户页的搜索与排序、错误页的查找、审计页不进地址（本次不做）。

## 5. 运营概览

### 5.1 布局

```
[未定价模型提醒条 —— 整条可点 →]                         （有未定价模型才出现）

┌用户──────┐ ┌7 天活跃──┐ ┌30 天金额─┐ ┌7 天失败──┐
│ 128      │ │ 41       │ │ $86.20   │ │ 3        │
│近7天新增5│ │占全部32% │ │近7天$21  │ │最近一次… │
│          │ │          │ │ ∿∿∿∿∿∿   │ │          │
│查看用户 →│ │查看用户 →│ │查看用量 →│ │去处理 →  │
└──────────┘ └──────────┘ └──────────┘ └──────────┘
┌运行中任务┐ ┌30 天token┐ ┌近 14 天每日金额──────────┐
│ 2        │ │ 1,234,567│ │                          │
│其中排队1 │ │30天调用… │ │      （折线图）          │
│查看任务 →│ │查看用量 →│ │                          │
└──────────┘ └──────────┘ └──────────────────────────┘
┌任务状态──┐ ┌用户状态──┐ ┌30 天金额 · 按模型─┐
│排队中  1 │ │正常  120 │ │model-a     $60.10 │
│运行中  1 │ │已停用  8 │ │model-b     $26.10 │
│近7天失败3│ │其中管理员│ │model-c     未定价 │
│查看任务 →│ │查看用户 →│ │查看全部 →         │

```

宽屏四列；中等宽度两列（趋势图占满一行）；分布卡片中等宽度以上三列、窄屏一列。

卡片文案沿用现有叫法（「金额」「token」），不改成「花费」「tokens」，免得同一个后台里两套说法。

### 5.2 数据来源

概览页用四份现有数据。**第一份是主数据**，失败时整页显示错误条；**后三份是补充数据**，各自独立请求，哪一份失败或还没到，依赖它的副标题与卡片就不显示，页面其余部分照常。

| 代号 | 接口 | 前端函数 |
| --- | --- | --- |
| O | `GET /admin/overview` | `adminOverview()`（由外框取，每 30 秒刷新） |
| U | `GET /admin/users` | `adminUsers()` |
| J | `GET /admin/jobs` | `adminJobs()` |
| M | `GET /admin/usage?group=model&days=30` | `adminUsage('model', 30)` |

标题行的「刷新」把四份都重新取一遍。

### 5.3 每个数字的来源

| 位置 | 显示 | 来源与算法 | 行动链接 |
| --- | --- | --- | --- |
| 用户 · 数字 | 用户总数 | O.`users` | 查看用户 → `/admin/users` |
| 用户 · 副标题 | 近 7 天新增 N | U：`created_at` 在 7 天内的用户数 | |
| 7 天活跃 · 数字 | 近 7 天活跃用户数 | O.`active_7d` | 查看用户 → `/admin/users` |
| 7 天活跃 · 副标题 | 占全部用户 P% | O.`active_7d` ÷ O.`users`，四舍五入；`users` 为 0 时不显示 | |
| 30 天金额 · 数字 | 美元两位小数 | O.`cost_30d` | 查看用量 → `/admin/usage` |
| 30 天金额 · 副标题 | 近 7 天 $X | O.`daily` 最后 7 项的和；`daily` 为空时不显示 | |
| 30 天金额 · 趋势线 | 迷你折线 | O.`daily` 全部 30 天（沿用现有 `Sparkline`） | |
| 7 天失败 · 数字 | 失败任务数，大于 0 标红 | O.`failed_7d` | 去处理 → `/admin/jobs?state=failed` |
| 7 天失败 · 副标题 | 最近一次 MM-DD HH:MM | J.`failed[0].created_at`（接口已按时间倒序）；没有失败时不显示 | |
| 运行中任务 · 数字 | 排队加运行中的任务数 | O.`running` | 查看任务 → `/admin/jobs?state=running` |
| 运行中任务 · 副标题 | 其中排队 N | J.`running` 里 `status === 'queued'` 的条数 | |
| 30 天 token · 数字 | 千分位 | O.`tokens_30d` | 查看用量 → `/admin/usage` |
| 30 天 token · 副标题 | 30 天调用 N 次 | M.`rows[].calls` 之和 | |
| 近 14 天趋势图 | 每日金额折线 | O.`daily` 最后 14 项（沿用现有 `LineChart`） | |
| 任务状态分布 | 排队中 / 运行中 / 近 7 天失败 | J：`running` 按 `status` 分，`failed.length` | 查看任务 → `/admin/jobs` |
| 用户状态分布 | 正常 / 已停用，另一行「其中管理员 N 人」 | U：`disabled`、`role` | 查看用户 → `/admin/users` |
| 30 天金额按模型 | 金额最高的 5 个模型，其余合并成「其他 N 个模型」；整行未定价的显示「未定价」并排最后 | M.`rows`（`cost_usd`、`unpriced`、`records`） | 查看全部 → `/admin/usage?group=model` |
| 未定价提醒条 | 未定价模型：a、b（不计入金额…） | O.`unpriced_models`；整条是链接 | `/admin/usage?group=model` |

「近 7 天」一律是滚动的 7×24 小时（和后端 `active_7d`、`failed_7d` 的算法一致），用浏览器当前时间算；文案写「近 7 天新增」而不是「本周新增」，避免被理解成自然周。

每条分布行带一条占比条：任务状态以三项之和为分母，用户状态以用户总数为分母，按模型以 30 天金额合计为分母（合计为 0 时占比为 0）。

### 5.4 拿不到所以不显示的数字

现有接口给不出下面这些，本次**不显示，也不加接口**：

| 想要的数字 | 为什么拿不到 | 决定 |
| --- | --- | --- |
| 任务状态分布里的「已完成 / 成功」「已取消」 | `GET /admin/jobs` 只返回内存里排队与运行中的任务，以及磁盘上近 7 天失败的版本；成功的不在返回里 | 分布卡片只列排队中、运行中、近 7 天失败三行，卡片底部写一行「只统计排队、运行中与近 7 天失败的任务。」 |
| 各卡片的「较上周 ±N%」环比 | 概览只有当前值；`daily` 只有金额一个序列 | 不显示。金额卡用「近 7 天 $X」代替 |
| 7 天活跃的趋势、活跃用户的新增 | 只有一个 `active_7d` 当前值 | 副标题改用「占全部用户 P%」 |
| token 的每日趋势、近 7 天 token | `daily` 里没有 token | token 卡的副标题用「30 天调用 N 次」（来自 M） |
| 运行中任务的「平均耗时」「最长等待」 | 可以从 J 的 `elapsed_sec` 算，但属于新统计 | 不做（§2 非目标） |
| 按用途（转换 / 章后整理）的金额分布 | `adminUsage` 只能按用户、天、模型分组 | 不显示 |
| 用户分布里的「从未登录」「本月超上限」 | 前者能从 U 算但属于新统计；后者需要逐个比较上限，也是新统计 | 不做 |
| 错误的「未处理数」 | 错误记录没有处理状态 | 导航计数用「近 7 天条数」，并在说明里写清口径 |

另外，补充数据（U、J、M）某一份请求失败时：

- U 失败：没有「近 7 天新增」副标题，没有用户状态分布卡片。
- J 失败：没有「最近一次」「其中排队」副标题，没有任务状态分布卡片。
- M 失败：没有「30 天调用」副标题，没有按模型分布卡片。
- 三份都失败：整个分布区不出现；六张数字卡与趋势图仍在。

这是「拿不到就省略」，不弹错误，也不留空壳卡片。

## 6. 组件与文件

都在 `frontend/src/components/admin/` 下，除非另外写明。

| 文件 | 变化 | 职责 |
| --- | --- | --- |
| `frontend/src/paths.ts` | 改 | 后台的页与筛选取值、`adminPath`、`parseLocation` 的后台分支 |

## 8. 风险与取舍

- **后台里没有产品顶栏的功能**（任务铃铛、助手、退出）。管理员要用这些得先「返回产品」。这是独立一屏的代价，换来的是结构干净、`AppShell` 不动。
- **概览多了三个请求**（用户列表、任务、按模型用量）。它们只在打开概览页和点刷新时各发一次，不轮询；轮询的仍然只有概览接口（30 秒）与错误列表（60 秒，给导航计数用）。
- **「近 7 天」用浏览器时间**。浏览器时钟偏差会让「近 7 天新增」「近 7 天错误数」在边界上差一两条，可以接受。
- **错误计数的上限**：列表接口最多 200 条，近 7 天超过 200 条时徽标显示「99+」，不会显示错的具体数字。
- **旧地址**：只有 `/admin` 一个，仍然有效（就是运营概览），没有需要兼容的旧链接。
